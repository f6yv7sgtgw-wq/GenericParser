# GenericParser 0.45.2 Build 6

## Zweck

Build 6 ist ein Integrations-Hotfix für Evercade Next. Die Suchruntime bleibt unverändert auf `0.45.0` mit den Referenzen `0.44.4` / `0.44.6.5`. Geändert werden ausschließlich Transport-/Kompatibilitätsschicht und Alias-Vertrag.

## Behobene Punkte

1. `/api/module/search` akzeptiert neben dem kanonischen `ModulePageRequest` mit `profile` auch das bisher von Evercade Next verwendete flache Requestformat. Das flache Format wird ausschließlich am Alias-Endpunkt in ein kanonisches `ModulePageRequest` übersetzt. `/api/module/v1/search` bleibt strikt und unverändert.
2. Die Browser-CORS-Schicht aus Build 5 bleibt unverändert erhalten.
3. Das alte Evercade-Payload wird auf folgende Profilfelder abgebildet: `query`, `required_terms`, `excluded_terms`, `model_patterns`, `brands`, `max_price`, `market_value`, `postal_code`, `location_id`, `radius_km`, `accept_bundles`, `accept_incomplete`, `include_review`, `include_rejected`, `sort_by`.
4. `profile_id` wird aus `cartridge.key`, sonst `profile_id`, sonst `evercade-legacy` erzeugt. `display_name` verwendet `cartridge.title`, sonst `query`.
5. Unbekannte Integrationsmetadaten wie `contract`, `adapter`, `mode` und `cartridge` werden nicht an den Suchkern weitergereicht.

## Nicht geändert

- Suchruntime
- HTML-Parsing
- Pagination
- Filterlogik
- Ranking
- Recovery
- Referenzkern

## Verifikation

Nach Deployment müssen folgende Browserpfade geprüft werden:

- GET `/health` → 200
- GET `/version` → 200
- GET `/diagnostics` → 200
- OPTIONS `/api/module/search` → 204
- POST `/api/search` mit Legacy-Payload → 200
- POST `/api/module/search` mit bisherigem Evercade-Payload → kein 422-Schemafehler
- POST `/api/module/v1/search` mit kanonischem `profile`-Payload → weiterhin erfolgreich
